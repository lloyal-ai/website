What are Lloyal Abilities — and how do they compare with DeepSeek Harness plugins?

Plugins compose the environment. Abilities compose the execution.

Lloyal Labs
August 2026

Plugins once meant a Tool registry and a callback. DeepSeek Harness and Lloyal have both moved beyond that boundary, in different directions.

DeepSeek Harness uses Cordis to make the software environment composable. Models, Tools, sandboxes, storage, interfaces and the Agent loop can be introduced as plugins whose services, visibility and lifetimes vary by scope and over time.

A Lloyal Ability is also an installable software package. It can contribute Tools, Sources, instructions, supporting models and protected operations. The difference appears when that capability is used: its work enters the application’s structured lifetime from a particular live inference lineage, under the harness’s policy and authority.

That last phrase depends on a different meaning of Agent than most frameworks use:

In Lloyal, an Agent is a branch of live inference state with intent.

The branch carries the live model state—its cells, position, sampler and continuation. TypeScript supplies its interpretation and decides what happens next.

One difference is worth stating before the comparison begins: DeepSeek Harness is built around DeepSeek’s own models, while Lloyal ships no model at all. The harness runs open weights you choose — GLM, Qwen, Llama — in your own process.

The comparison begins with the environment DeepSeek makes composable, then follows a Lloyal Ability across the point where installation becomes live execution.

What DeepSeek plugins make composable

DeepSeek Harness is assembled through Cordis, an independent meta-framework that has been the plugin kernel behind Koishi for four years and is now vendored as @deepseek-ai/cordis (tutorial). A plugin occupies a context, provides and consumes services, contributes registrations and owns the effects created through that context.

Cordis calls this paradigm spatiotemporal composability, and its own paper defines the two dimensions precisely: temporal composability is the ability to completely revert a component’s side effects upon removal; spatial composability is the ability to declare and reactively manage inter-component dependencies.

Scope is the arrangement those dimensions operate within. A deployment-level plugin may contribute a model service or Tool registry visible throughout the application. A plugin mounted beneath an Agent context can contribute Tools, prompt material and event handling to that Agent alone. Service names live in one flat namespace per application; it is the scoped contributions — tools, prompt sections, listeners — that a nearer context refines for a particular Agent.

The spatial dimension is dependency. A plugin declares required services through inject. If a dependency is absent, activation waits. When the service appears, the plugin enters the graph. If the provider is removed or replaced, dependent plugins unwind and can activate again when their requirements are satisfied.

deployment context
├── model service
├── persistence service
├── Tool registry
├── interface
└── Agent context
    ├── prompt contribution
    ├── Agent-local Tool
    └── decision hook

The temporal dimension is withdrawal. A Cordis fiber owns the registrations and effects associated with a plugin’s presence. Removing the fiber removes those contributions; replacing a service causes dependants to unwind and reactivate against the new provider. The context graph remains mutable without making lifecycle an informal convention.

This is not adequately described as a function receiving Tool arguments. An Agent-scoped plugin inhabits the Agent’s model-facing environment. It can resolve live services, contribute Tools and prompt material, observe scoped events and remain present for the lifetime of its context.

What an Ability packages

A Lloyal Ability is a signed, installable capability for Agents inside an application harness.

Its package can declare:

  • Tools exposing operations to the model;
  • a skill describing how those operations should be used together;
  • Sources through which external or changing state becomes perceptible;
  • configuration binding the capability to a deployment or domain instance;
  • services, including specialist models the runtime must provision;
  • grants required before protected operations may run;
  • a protocol describing when the capability should enter attention.

The service boundary includes more than ordinary application dependencies. An Ability can declare a second model with its own execution state. The Corpus Ability, for example, can use a cross-encoder reranker provisioned at boot. An OCR Ability can similarly rely on a specialist vision model. Those services may batch their own work independently of the primary generative model.

At installation, an Ability is still recognisable as a versioned software package. The architectural difference begins when a live branch invokes one of its Tools.

Two trees, one running application

Cordis and Effection both contain contexts, scopes, effects and cleanup. Their primary guarantees concern different structures.

Cordis records the changing software environment. Effection records causal ownership in the execution underway. Work started beneath an operation cannot silently outlive that operation. Interruption follows the structure by which the work was created; cleanup settles before the responsible scope disappears.

That lifetime tree is one half of Lloyal’s runtime architecture.

The left side is ordinary TypeScript. withSpine opens a scope holding a live line of attention. agentPool creates a cohort inside it. Tool work and delegated pools enter scopes of their own.

The right side is live inference state. The spine’s system-and-Tools header is decoded once and shared. Each Agent branch owns the cells above its fork head while retaining shared tenancy over everything below it.

TypeScript lifetimes                 live inference state

harness scope                        shared spine
└── withSpine                        └── decoded trunk cells
    └── Agent pool                       ├── branch A
        ├── branch interpretation         ├── branch B
        │   └── Tool scope                │   └── delegated branch B1
        └── branch interpretation         └── branch C

The two trees are the same running application represented at different altitudes.

The correspondence is enforced rather than advisory. A fork registers cleanup in the lifetime that created it. A TypeScript scope cannot disappear while silently abandoning its native state.

The lifetime tree therefore proves which work cannot survive its scope. The inference-state tree records which cells that work is responsible for. An Ability may create requests, supporting-model operations and delegated branches; all remain attached to the application lifetime that admitted them.

The invocation boundary

In a conventional harness, a Tool call commonly leaves inference as an argument object. The host executes code, serialises the result and sends another model request. The Tool participates in a loop around inference.

In Lloyal, model execution is resident application state. The branch that produced the Tool call remains addressable while the application handles it. The Tool operation begins beneath the application scope responsible for that branch, and its result can be admitted back into the same live lineage.

live branch produces Tool call
└── application enters Ability operation
    ├── external request
    ├── supporting-model work
    ├── progress to product surface
    └── optional delegated pool
        ├── child branch A
        └── child branch B

The Ability does not receive an abstract right to control the Agent. Its Tool receives a concrete context from the harness: Agent identity, the calling branch where required, progress reporting and runtime signals supplied by the pool.

The calling branch remains the cognitive ground truth. The Ability contributes application capability around it.

The inheritance contract

Forking live model state does not copy the application environment into a child.

A branch inherits cognitive state:

  • the decoded KV prefix;
  • the shared spine header;
  • format configuration;
  • an optional seed.

It does not inherit application judgment:

  • policy;
  • guards;
  • grants;
  • the Tool registry;
  • Tool history as mutable state.

State inherits; judgment doesn’t.

Policy, authority and capability surface are established by the pool into which the branch is admitted. Tool history can be inspected across a lineage when a guard or capability needs it, but it is not embedded into the child’s inherited model state.

Cordis ancestry determines which software contributions a child context can resolve. Lloyal branch ancestry determines which decoded model state a continuation begins from. Structured concurrency determines which application lifetime remains responsible for it. None of those relationships implies the other two.

An Ability visible to a parent is not necessarily visible to a delegated pool. A child beginning from the parent’s live state does not acquire the parent’s grants. A lifetime-bound operation is not authorised merely because it cannot outlive its caller.

The harness makes each decision explicitly.

Policy and authority remain with the application

The branch carries state, not judgment. AgentPolicy governs how the pool interprets and advances that state: before decode, after a structured result, during dispatch, on Tool failure, through recovery and when the pool must settle or stop.

An Ability can respond to policy-derived conditions without acquiring the policy itself. The harness may pass exploration posture and remaining attention headroom into a Tool invocation. The Tool adapts its operation; the application retains the decision that produced those values.

The shipped Corpus Ability demonstrates the seam. Its search Tool can preserve broader, branch-local ranking during exploration, then apply tighter dual scoring when policy moves the pool into exploitation. A separately provisioned cross-encoder evaluates candidate material. The available attention budget travels with the dispatch, allowing evidence selection to respond before an oversized result is admitted into live state.

Retrieval is not a detached database step followed by another request. It participates in the running application’s admission policy while the calling branch remains alive. The Ability supplies the capability; the harness decides when it participates, which branch receives its result and whether execution continues.

Abilities may also expose protected Tools. Grants are resolved for the application session and checked before those operations run. An Agent can see a Tool without being authorised to create its external consequence. A model can select it without bypassing the grant boundary. A child branch can inherit live state without inheriting its parent’s authority.

Signing establishes provenance rather than permission. The Ability channel distributes reviewed packages signed with an Ed25519 key. The attention surface is derived from the published package and can be inspected before its implementation runs. The signature ties the declared capability to the reviewed bytes; grants determine what those bytes may do in a particular session.

Provenance is not authority. Authority is not policy. Policy is not inherited state.

The extension boundaries compared

These are the contracts made structural by the current systems, not limits on what either project could theoretically implement.

Where the architectures meet

Cordis can compose the providers, registries and interfaces surrounding an inference runtime. Structured concurrency can govern the work a plugin starts. An Ability can call an MCP server where process isolation, remote placement or language independence is preferable to in-process access.

Lloyal Abilities occupy the point where an installed capability enters an application’s live inference topology: from a defined branch, within a defined lifetime, under policy and authority that state inheritance cannot confer.

An Ability extends what an application’s intelligence can do without becoming independent of the application that governs it.
