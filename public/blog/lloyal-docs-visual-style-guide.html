Lloyal Programming Guides — Visual Style Guide

Lloyal Programming Guides — Visual Style Guide

Status: extracted from the August 2026 programming-guide system: the docs index, Build your first harness, Thinking in Lloyal, How Agents Know When to Stop, and Where a harness runs, plus the comparison, platform-map, and CLI visuals.

1. Visual thesis

The Lloyal guides should feel like an engineering journal that contains an executable system.

The visual language combines:

  • editorial authority — large compressed headlines, generous white space, publication metadata, black thesis bands;
  • systems precision — ruled grids, restrained monochrome diagrams, explicit hierarchy, dense but calm reference layouts;
  • executable reality — dark code frames, terminal captures, monospace structures, concrete commands;
  • institutional restraint — almost no decorative colour, no gradients in the document chrome, minimal rounding, and no generic SaaS-card softness.

The governing principle is:

Use typography and structure to create force. Use colour only to encode executable material.

The pages are not visually “futuristic AI.” They are sober, technical, and publication-like. Intelligence is presented as infrastructure that can be inspected and programmed.

2. Design character

Five characteristics should survive every extension of the system:

  1. Monochrome first. White paper, near-black ink, grey hierarchy, hairline rules.
  2. Scale creates emphasis. Headlines become large and tightly tracked; ordinary components do not become colourful.
  3. Borders create structure. Cards, tables, paths, status columns, and navigation use shared rules rather than shadows and isolated boxes.
  4. Darkness marks a conceptual or executable boundary. Black thesis bands, code blocks, mini diagrams, and terminal captures signal a change of mode.
  5. The page remains a document. Even interactive elements should retain the feel of an engineered publication.

3. Typography

3.1 Primary typeface

Use Readex Pro Variable for all editorial and interface typography.

font-family: "Readex Pro Variable", "Readex Pro", "Inter", Arial, sans-serif;
font-weight: 300;

Use the variable font across weights 100–900. The default page voice is light (300), with emphasis concentrated at 500–600. Avoid conventional heavy body copy or 700–800 headings; the identity comes from scale, spacing, and Readex Pro's shape rather than blunt weight.

3.2 Monospace typeface

Use the platform-native technical stack:

font-family: "SFMono-Regular", Consolas, "Liberation Mono", monospace;

Mono is reserved for:

  • code and terminal commands;
  • file trees and structural diagrams;
  • sequence numbers and compact technical identifiers;
  • inline code;
  • exact runtime or configuration values.

Do not use monospace as a general “developer aesthetic” decoration.

3.4 Typographic voices

The system has three distinct voices.

Editorial voice

Used for page titles, article headings, theses, pull quotes, and explanatory prose.

  • large headings;
  • tight negative tracking;
  • light body copy;
  • sentence case;
  • strong line-length discipline.

Operational voice

Used for masthead metadata, eyebrows, table headers, code labels, path labels, status and card kickers.

  • 9–10px;
  • uppercase;
  • 0.10–0.20em tracking;
  • medium weight;
  • grey unless active.

This voice makes the pages feel catalogued and engineered.

Executable voice

Used for code, commands, structures, paths and exact values.

  • monospace;
  • dark framed surfaces for block content;
  • pale neutral background for inline code;
  • no decorative italics or terminal-style effects in ordinary prose.

3.5 Responsive typography

At ≤900px:

  • index hero: 84px → 58px;
  • guide hero: 76–78px → 52–54px;
  • hero subtitle: 25–26px → 20–21px.

At ≤560px:

  • index hero: 46px;
  • guide hero: 43–44px;
  • hero subtitle: 18px;
  • article H1: 34px;
  • article H2: 24–25px;
  • article body: 15px;
  • pull quote: 22–23px.

Preserve tight display tracking at smaller sizes. Do not merely shrink the desktop layout proportionally.

4.3 Syntax colour

Colour is concentrated inside executable contexts. The code syntax palette is Monokai-derived:

  • cyan #66D9EF — language keywords;
  • pink #FF4689 — operators and declarations;
  • green #A6E22E — functions/names;
  • yellow #E6DB74 — strings;
  • purple #AE81FF — numeric and literal values;
  • muted olive-grey #959077 — comments;
  • code foreground #F8F8F2.

The CLI captures use a related but more luminous cyan → blue → violet → magenta identity, with orange section prompts and green success states. Keep that chromatic vocabulary inside terminals, product execution, and selected brand marks. Do not spread it into the editorial page chrome.

5. Page shell

5.1 Document-on-canvas composition

Desktop pages sit as a white publication sheet on a grey canvas:

body {
  margin: 0;
  background: #d8d8d8;
}

.page {
  max-width: 1180px; /* long-form guides */
  margin: 0 auto;
  background: #fff;
  min-height: 100vh;
  box-shadow: 0 18px 60px rgba(0,0,0,.16);
}

The index and broad architecture pages may widen to 1320px. Long-form programming guides use 1180px to keep article measure disciplined.

5.2 Horizontal padding

.wrap { padding-inline: 72px; }

@media (max-width: 900px) {
  .wrap { padding-inline: 28px; }
}

This 72px edge is a defining part of the publication feel. Do not replace it with a generic fluid 16–24px container on desktop.

5.3 Masthead

  • height: 108px desktop; 90px below 900px;
  • one hairline bottom border;
  • wordmark left, issue/category/date right;
  • no large logo or coloured navigation chrome;
  • wordmark: 16px/600 with -0.025em tracking;
  • tagline and issue metadata: 9px uppercase with approximately 0.20em tracking.

The masthead should feel like a journal issue, not an application navbar.

5.4 Hero

  • 70–76px top padding;
  • 66–70px bottom padding;
  • uppercase eyebrow first;
  • oversized, tightly tracked title;
  • lighter grey subtitle with a wide but bounded measure;
  • no decorative illustration beside the title.

The title creates the visual event.

5.5 Thesis band

The black thesis band follows the hero and changes the page from introduction to proposition.

  • full width of the white document;
  • 50–60px vertical padding;
  • one or two columns depending on page;
  • copy in #c7c7c7–#d0d0d0;
  • the decisive sentence or pull quote in white;
  • internal rules in #393939–#3a3a3a.

Use a thesis band once per page. Do not scatter black marketing panels throughout the article.

6. Long-form article layout

6.1 Two-column shell

.article-shell {
  display: grid;
  grid-template-columns: 235px minmax(0, 1fr);
  gap: 62px;
  align-items: start;
  padding-top: 64px;
  padding-bottom: 90px;
}

The sidebar is deliberately narrow and quiet. The article column receives the remaining measure.

At ≤900px, collapse to one column. The TOC becomes non-sticky and uses two columns; at ≤560px, it becomes one column.

6.2 Table of contents

  • sticky at top: 28px;
  • top hairline and no enclosing card;
  • 9px uppercase label;
  • 11px links;
  • fine bottom rule per link;
  • level 1 darker and medium weight;
  • level 2 indented 12px;
  • level 3 indented 24px, 10px and lighter;
  • active item: #111, weight 600.

The TOC is an index, not a second navigation product.

6.3 Article rhythm

  • H1 sections: 78–84px separation, 42px type;
  • H2: 52–64px separation, 1px top rule, 27–28px type;
  • H3: 38px top margin, 19px type;
  • paragraphs: 19px bottom rhythm;
  • horizontal section divider: 48px vertical margin;
  • lists: 8px between items;
  • links: 1px underline, 3px underline offset.

Use whitespace to mark semantic depth. Avoid coloured section backgrounds inside ordinary article flow.

7. Components

7.1 Code frames

  • background #070707;
  • border 1px solid #222;
  • no border radius;
  • uppercase 9px label in #999, separated by #292929 rule;
  • code padding 20px 22px 22px;
  • 13px mono at 1.6 line height;
  • horizontal overflow rather than forced wrapping for source code.

Labels describe the semantic mode: TYPESCRIPT, TERMINAL, STRUCTURE, FLOW. Do not label every code block simply “CODE.”

7.2 Inline code

  • 0.87em mono;
  • #efefef background;
  • 0.14em 0.35em padding;
  • 2px radius.

The tiny radius is functional, not a general rounded-card motif.

7.3 Model callouts

Used in the first-harness tutorial to connect a practical step to the programming model.

  • #f7f7f7 background;
  • 3px black left rule;
  • 16–18px internal padding;
  • uppercase 10px heading with 0.10em tracking;
  • 13px explanatory copy at 1.55.

Use callouts sparingly and only to expose an invariant that has just become concrete.

7.4 Blockquotes and principles

Ordinary blockquote:

  • pale grey background;
  • 4px black left border;
  • 18px text.

Load-bearing principle:

  • near-black background;
  • white text;
  • no left accent;
  • 21px/1.35 medium-weight type.

The distinction should communicate “supporting quotation” versus “governing law.”

7.5 Tables

  • no outer card;
  • collapsed borders;
  • horizontal rules only;
  • 13.5px body;
  • 10px uppercase headers with 0.10em tracking;
  • 12–13px cell padding;
  • final bottom rule.

Tables should resemble technical reference sheets, not dashboards.

7.6 Index path cards

  • shared two-column ruled grid, not floating cards;
  • 1px grey borders;
  • minimum height around 285px;
  • 32–34px padding;
  • mono sequence number;
  • title separated vertically from number;
  • categorical label pinned to the bottom;
  • hover inverts the entire cell to near-black.

Do not add per-card shadows, icons, gradients, or rounded corners.

7.7 Progression rail

The first-harness guide uses a six-cell ruled sequence:

  • one shared border;
  • equal-width cells;
  • 9px numbered metadata;
  • 11px/550 label;
  • fine chevron formed from borders between cells;
  • responsive 6 → 3 → 2 columns.

Use for a literal instructional sequence, not for unordered feature lists.

7.8 Status pills

Pills are an exception used only for compact state:

  • current: black fill, white text;
  • planned: pale fill, grey text and border;
  • 8px uppercase, tracked;
  • small 999px radius.

Never use pills for ordinary navigation or marketing categories.

7.9 Screenshots

Terminal screenshots sit in a dark frame matching the image background:

  • border 1px solid var(--line);
  • frame background approximately #0a0d18;
  • no decorative browser chrome;
  • full-width image;
  • optional dark caption strip with subdued blue-grey copy.

Keep screenshot sequences editorially economical. Each image should prove a state change, not merely show another prompt in the same wizard.

8. Diagrams

8.1 Diagram language

Information diagrams use:

  • white background;
  • black primary type and strokes;
  • pale blue-grey or neutral grey borders;
  • thin rules;
  • simple outline icons;
  • limited rounded rectangles;
  • ample internal white space;
  • uppercase group labels;
  • sentence-case explanatory copy;
  • no gradients, 3D arrows, glowing nodes, or decorative networks.

The visual objective is an architectural plate, not an AI infographic.

8.2 Hierarchy

Use dark weight and scale for the claim, not colour. Blue may appear as a very restrained explanatory accent, but it should not become a second brand system.

Recommended hierarchy:

  1. page/diagram thesis;
  2. major domain or layer;
  3. component label;
  4. mechanism or relationship;
  5. qualifier/current-planned note.

8.3 Conceptual fidelity

Diagrams must preserve the ownership distinctions in the prose:

  • policy decides; the pool prunes and enforces;
  • evidence is admitted to selected lineages, not globally broadcast;
  • zero-copy applies to inherited/shared prefix state, not every piece of branch state;
  • surface, location, operator and compute class are separate axes;
  • planned capabilities must be visibly distinct from current ones;
  • control during inference supplements rather than eliminates final validation.

When a diagram simplifies one of these distinctions, add a local qualifier rather than relying on a distant caption.

8.4 Wide diagrams

Wide architecture plates may use a minimum intrinsic width around 920px inside a horizontally scrollable container. On print, remove the minimum width.

Avoid scaling dense text below readable size merely to make the whole plate fit a phone viewport.

9. CLI visual system

The CLI is a related sub-system, not the web page palette.

Typography

  • terminal/system monospace;
  • generous line spacing;
  • large enough to remain readable in documentation screenshots;
  • bold used for commands, chosen values and state transitions.

Colour roles

  • cyan/blue/violet/magenta: harness.dev identity and major selection focus;
  • orange: prompt category and action heading;
  • cyan: active selection;
  • green: selected/success/ready;
  • white: executable command and primary output;
  • cool grey: instructions, secondary values and inactive state;
  • near-black navy: terminal background.

Composition

  • large logo and product descriptor establish identity once;
  • wizard content is left aligned and vertically staged;
  • current question receives colour and weight;
  • completed values recede into grey summaries;
  • successful completion presents the exact next commands.

Do not imitate the CLI gradient inside article headings or general UI controls. The contrast between monochrome editorial shell and chromatic executable surface is intentional.

10. Interaction

  • cards invert black on hover;
  • text links retain normal document underlines;
  • external links use a compact arrow glyph/mask;
  • TOC active state changes colour and weight only;
  • back-to-top is a small squared control with a fine border;
  • transitions are short, approximately 180–200ms;
  • no spring motion, parallax, animated gradients, or attention-seeking hover elevation.

Interaction should reveal structure, not make the document feel like a product dashboard.

11. Responsive behaviour

Primary breakpoints:

  • 900px — collapse major grids, reduce page padding, move sticky TOC into flow;
  • 560px — compress display type, make TOC single-column, collapse comparison and reference grids;
  • component-specific 680px — collapse complex stack layers.

Rules:

  • preserve the document hierarchy on small screens;
  • collapse grids vertically rather than shrinking type excessively;
  • keep code horizontally scrollable;
  • allow dense architecture diagrams to scroll horizontally;
  • keep metadata visible but reduce its gap;
  • never hide planned/current qualification to save space.

12. Do / do not

Do

  • lead pages with one large claim;
  • use black bands for the governing proposition;
  • use thin shared rules to build grids;
  • keep body copy light and highly readable;
  • reserve mono for exact technical material;
  • make category metadata small, uppercase and tracked;
  • use diagrams to clarify ownership, topology or placement;
  • use screenshots to prove executable reality;
  • preserve generous vertical intervals between conceptual levels.

Do not

  • add generic AI gradients to page chrome;
  • use glassmorphism, glowing network graphics or blurred colour fields;
  • round every container;
  • place every idea in an isolated card;
  • bold whole paragraphs;
  • use colour as a substitute for hierarchy;
  • use mono as decorative body type;
  • show a feature as current when it is planned;
  • collapse policy, execution, authority and continuity into one visual actor;
  • overfill tutorials with nearly identical screenshots.

14. The shortest usable definition

When making a new Lloyal programming-guide page, use this test:

Does it look like a serious engineering publication until executable material enters the page—and does that executable material feel unmistakably alive?

If the page looks like a SaaS landing page, it has drifted. If it looks like an academic PDF, it has lost the product. The Lloyal system lives precisely between those two states.
